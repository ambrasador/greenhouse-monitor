# Код розділів 1–7: Greenhouse Monitor

Робочий застосунок із підручника «Технології розробки додатків для інтернету речей»: модуль приймання телеметрії (розділ 1), REST API над ним (розділ 2), канал даних реального часу з клієнтом для браузера (розділ 3), вебдашборд з історією, кешем запитів та експортом (розділ 4), мобільний клієнт на Flutter із серверною частиною push-сповіщень (розділ 5), захист застосунку: вхід, ролі й область доступу, підписаний вебхук, журнал аудиту, приватність (розділ 6) та експлуатація: піраміда тестів на Jest і `node:test`, образи Docker і стек Compose, конвеєр CI, міграції бази, журнал, метрики й сповіщення (розділ 7), разом із тестами та сценаріями, якими виміряно числа з тексту. Усе, що наведено в лістингах підручника, взято з цих файлів без змін; діапазони рядків у підручнику відповідають цій версії.

## Запуск

Потрібен Node.js 22 або новіший.

```
npm ci
npm test
```

Очікуваний результат: 345 тестів (на 12 більше, ніж у розділі 6), усі пройдені (близько 20 с на двох vCPU). Тести працюють без зовнішнього брокера й без мережі: джерело повідомлень і приймач команд підставлено, база лежить у пам’яті. Тести розділу 6 піднімають сервер із увімкненою безпекою (`auth-kit.js`) з приглушеним scrypt. Тести каналу реального часу (`realtime`, `sse`, `ws-frame`, `client/*`) піднімають справжні сервери на вільних портах localhost. Виняток — `e2e-mqtt.test.js`: він запускає брокер Aedes у тому самому процесі й перевіряє пристрій, підтвердження та недоступний брокер на справжньому з’єднанні MQTT.

Демонстрація в браузері (графік температури з історією за 5 хвилин і живим потоком):

```
npm run build:client
node demo.js
```

`demo.js` запускає стенд із брокером, приймачем, API й генератором вимірювань і виводить три адреси сторінки: для Socket.IO, SSE та MQTT через WebSocket. Зупинка — Ctrl+C.

Дашборд розділу 4 (картки статусів, історія за 1 год, 24 год і 7 днів, експорт у CSV, живі точки для «Грядки А»):

```
npm run build:client
npm run demo:dashboard
```

Скрипт виводить адресу сторінки `dashboard.html`. Наскрізну перевірку дашборда в Chromium (23 перевірки: статуси, старіння даних, діапазони, експорт, цілі натискання, екран 320 px) запускає `npm run e2e:dashboard`; вона потребує `npx playwright install chromium` і зібраного клієнта.

Мобільний клієнт розділу 5 — Flutter-пакет у каталозі `mobile/`. Потрібні Flutter 3.47.9 (Dart 3.13.7); докладно — у `mobile/README.md`:

```
cd mobile
flutter pub get
flutter analyze
flutter test test/*.dart
BED_DIR=.. flutter test test/integration
```

Очікуваний результат: «No issues found!», 135 тестів без емулятора й 21 інтеграційний проти справжнього еталонного сервера (їм потрібні `npm ci` у цьому каталозі й змінна `BED_DIR`).

Запуск самого застосунку потребує брокера MQTT і секретів (розділ 6): без `JWT_KEYS`, `JWT_CURRENT` і `WEBHOOK_SECRETS` сервер не стартує, а повідомлення називає всі проблеми конфігурації одразу.

```
export JWT_KEYS="k1:$(openssl rand -base64 32)" JWT_CURRENT=k1
export WEBHOOK_SECRETS="$(openssl rand -hex 32)"
export DB_FILE=./greenhouse.db
NEW_PASSWORD='не менше 15 символів' node admin-cli.js user-add admin admin
MQTT_URL=mqtt://localhost:1883 PORT=3000 npm start
```

Першого адміністратора створює `admin-cli.js`: HTTP-кінцевої точки для облікових записів немає. Явне `AUTH_DISABLED=1` вмикає режим розділів 1–5 без входу й ролей; порожнє середовище захисту не вимикає.

Змінні середовища: `MQTT_URL`, `DB_FILE`, `PORT`, `DB_SYNC` (`FULL` за замовчуванням або `NORMAL`; вибір пояснено в розділі 1.4.4). Змінні розділу 6: `JWT_KEYS` (пари `kid:base64` через кому, ключ від 32 байтів), `JWT_CURRENT` (`kid` ключа, що підписує нові токени), `WEBHOOK_SECRETS` (через кому, новий першим, кожен від 32 символів), `INGEST_DEVICES` (регулярний вираз ідентифікаторів пристроїв, яким дозволено вебхук), `ALLOWED_ORIGINS` (дозволені `Origin` для WebSocket, через кому; порожній перелік відхиляє будь-який браузерний `Origin`), `AUTH_DISABLED`. Маршрути API описано в `openapi.yaml`, потік SSE — `GET /api/v1/devices/{id}/stream`; Socket.IO слухає на тому самому порту.

Специфікацію перевіряє лінтер Redocly: `npm run lint:api`. Очікуваний результат: документ валідний, без попереджень (схеми безпеки описано в розділі 6).

`npm audit` повідомляє про 25 знахідок у всьому дереві залежностей (3 низького рівня й 22 помірного): усі лежать у ланцюгах Jest, ESLint і `autocannon`, тобто в інструментах розробки, і в образ не потрапляють; `npm audit --omit=dev` не знаходить жодної.

Тести, перевірки й стек розділу 7 (докладно — у розділі «Файли розділу 7» і в підручнику):

```
npm run test:jest        # Jest: 18 модульних, 5 інтеграційних і 2 наскрізні тести
npm run test:coverage    # модульні й інтеграційні тести Jest із покриттям; поріг 85 % рядків і 70 % гілок
npm run lint             # ESLint 10, нуль зауважень
npm run test:rules       # promtool: 14 тестів правил сповіщень (потрібен Docker)
./smoke.sh               # образи, Compose і показання від брокера до проксі (потрібен Docker)
```

Наскрізним тестам Jest потрібні зібраний клієнт (`npm run build:client`) і Chromium (`npx playwright install chromium`). Стек піднімає `docker compose up -d --wait` (потрібен файл `.env`: скопіюйте `.env.example` і замініть секрети; `smoke.sh` без `.env` створює одноразовий). Дашборд — на `http://localhost:8080`, брокер для імітатора пристроїв — на `127.0.0.1:1883`; сторінка `/metrics` проксі назовні не віддає, усередині мережі Compose її читають командою `docker compose exec web wget -qO- http://backend:3000/metrics`. Рівень журналу задає змінна `LOG_LEVEL` (`info` за замовчуванням).

## Обмеження вимірювань

- Двоядерна віртуальна машина: сервер, клієнти стенду й Chromium ділять процесор, тому всі числа — оцінка зверху на вартість, а не паспортні дані.
- Кожна клітинка таблиці штормів — один прогін; три прогони є лише в наскрізній перевірці (таблиця 3.8).
- У наскрізних прогонах `retry` для SSE становить 0,5–1 с замість 3–6 с, які використовує застосунок.
- Байти на дроті — прикладного рівня: без TLS і без заголовків TCP/IP.
- Кілька екземплярів, спільні підписки MQTT 5.0 і вихідна черга в базі в розділі 3 описано, а не запущено.
- Розділ 4: дані синтетичні (зерно 42), Chromium 153 малює програмно, без GPU; кожне значення часу — медіана трьох–семи прогонів, розкид мікровимірювань сягає 50 %.
- Розділ 4: кількість запитів і з’єднань міряють у робочій збірці; у режимі розробки `StrictMode` додає два запити.
- Розділ 4: зчитувачі екрана (NVDA, VoiceOver) не запускали; доступність перевірено за розміткою й автоматичними тестами.
- Розділ 5: емулятор і телефон не запускали, плагін BLE не підключали, `firebase_messaging` лише скомпільовано; вигляд на пристрої, швидкість відмальовування, поведінку таймерів у фоні та мережу оператора не вимірювали.
- Розділ 5: імітація FCM відтворює контракт HTTP v1, а не сервери Google; успіх у стенді не доводить доставки на телефон.
- Розділ 5: M1, M2 і M10 міряють на localhost з *RTT* близько 3 мс; значення M2 і M10 від прогону до прогону трохи відрізняються (мітки часу, випадкові паузи перед повтором): найбільша похибка M2 — 498 мс у книжці й 502 мс у повторному прогоні на чистій копії, число відповідей 429 у сценарії `async*` M10 — 14 і 12 (скасування SSE: 14,62–14,68 с проти 0–2 мс в обох); M1 повторюється за зерном проксі, M3, M6, M8, M11 і M13 відтворюються точно (звірено на чистій копії архіву 05.11.2026).
- Розділ 5: параметри доменів у `calc5-domains.py` — навчальні припущення, а не дані реальних систем.
- Розділ 6: усі виміри — на двох vCPU; M1–M3 залежать від частоти й кількості ядер. Абсолютні часи залежать і від набору інструкцій процесора. Числа підручника виміряно на ВМ, де HMAC-SHA256 над тілом 256 КіБ займав 181 мкс (1,45 ГБ/с — швидкість, типова для апаратних інструкцій SHA). Повторний прогін на чистій копії відбувся на іншій ВМ (теж два vCPU Xeon 2,8 ГГц, але `sha_ni` у `/proc/cpuinfo` немає, що, імовірно, і є причиною): те саме тіло — 686 мкс (0,38 ГБ/с), PBKDF2 із 600 000 ітерацій — 268 мс замість 91, швидкість SHA-256 у циклі підбору — 0,68 замість 1,25 млн хешів за секунду, scrypt *N* = 2^15, *p* = 3 — 255 мс замість 223. Висновки збіглися: різниці за часом відповіді в M3 немає (імовірність 0,49 проти 0,50), шлюз приймає 34 входи зі 100 і відхиляє 66, найбільший інтервал таймера в режимі шлюзу — 12 мс проти 13 у книжці, байти на запис (117 для кешу повторів, 305 для refresh-токена, 127 для журналу) збігаються. Звіряйте співвідношення, а не абсолютні мілісекунди; на своєму процесорі зніміть власні значення. У M5  клієнт і сервер ділять процесор, тому вартість автентифікації подано як процесорний час сервера на запит (`process.cpuUsage()`), а не лише як різницю пропускної здатності.
